# 保险库保存评审

## 目标与范围

保证单个 Keyward 服务进程内的保存按顺序执行，拒绝标签页用旧内容覆盖新内容，并仅在服务端确认保存后提交界面中的修改。保留现有加密信封格式，不增加同步、自动合并或主密码变更。

## 已核实的调用与问题

基线 `b43a30d`：`src/web/app.js` 的创建、编辑、收藏和删除均调用 `persist()`，先更新明文状态再发送 PUT，保存异常被捕获后不再上抛。`unlock()` 会因此在首次保存失败后显示保险库。`src/server/server.js` 的 PUT 没有版本条件。`src/server/storage.js` 使用固定 `.tmp`，且备份与重命名之间没有并发协调。两个写入可能相互覆盖或遇到临时文件不存在。

请求均发到本机 `/api/vault`，浏览器使用原生 `fetch`，没有自定义连接池、超时或重试。此次不修改客户端共享网络配置，不增加自动重试；保存过程显示等待状态，锁定仍然可用。浏览器网络完成时间仍取决于运行环境，不能承诺固定总耗时。

## 方案与取舍

- 单纯串行写入能修复临时文件竞争，但不能识别来自旧标签页的修改。
- 自动合并需要定义条目编辑、删除及密钥变更之间的业务规则，超出当前范围。
- 采用密文内容的 SHA-256 摘要作为 revision。GET 返回 revision 和 ETag（HTTP 内容版本标识）；创建使用 `If-None-Match: *`，更新使用 `If-Match`。服务端在同一路径的写入队列内比较 revision，冲突返回 412，不改保险库或备份。相同密文重试视为成功。
- 使用独立临时目录生成保险库与备份文件，权限均为 `0600`，通过重命名发布。只把 ENOENT 视为缺失；损坏内容和文件系统错误不能转为新建流程。
- 浏览器的保存逻辑抽成可测试模块，保存确认后才更新内存中的保险库。保存失败时保留编辑表单供重试，冲突提示重新解锁并重新应用修改。锁定撤销待执行保存，并阻止异步结果重新发布明文，同时清理详情、编辑器和生成器 DOM。

未提供条件的旧客户端 PUT 返回 428，避免无条件覆盖；GET 及既有信封仍兼容。升级服务后旧页面需要刷新，已打开页面里的未保存内容需先保留。进程内队列不协调其他服务进程或手动文件写入，同一文件应只由一个服务进程管理。失败后不自动覆盖或重新加载，以便用户先保留编辑内容。

## 验证与回滚

回归测试覆盖同时创建、旧 revision、相同密文重试、并发存储、备份权限、损坏文件、写入错误、保存失败保留状态、队列顺序和锁定期间异步完成。本地 Node 22.23.3 和 Node 26.7.0 均通过 78 项测试，15 个 JS 文件的语法检查通过。保存保护修改后的浏览器交互尚未复验，仍需验证创建、编辑、冲突及锁定，不能以纯逻辑测试代替这项结果。

回滚对象为保存模块、服务端、前端和对应测试的代码修改；磁盘格式不变，原保险库可直接由旧版读取。回滚会恢复旧版无条件覆盖行为。`.bak` 是上一份已保存密文，不能代替尚未保存的编辑内容。
